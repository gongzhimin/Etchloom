# 文档系统组织与编写规范 (DOCUMENT_RULES)

> **规范编号**：STD-DOC-001  
> **适用范围**：全系统根 `docs/` 与所有一级、二级模块 `docs/`  
> **权威来源**：本项目架构设计与工业级文档工程标准  
> **更新策略**：严格遵循本规范定义的文件归属与单一真理源 (SSOT) 原则  

---

## 1. 文档系统架构与分工

本项目采用**两级分层、正交解耦、单一真理源**的文档架构体系：

```text
molandi_printmaking/
├── README.md                           # 项目入口说明 (快速开始、安装、运行、打包发布)
├── docs/                               # 【系统根文档】全局边界、跨模块契约与通用规范
│   ├── README.md                       # 文档系统总索引与导航 (不承担项目使用说明)
│   ├── requirements/
│   │   └── REQUIREMENTS.md             # 全局业务目标、场景、质量属性与验收标准
│   ├── design/
│   │   ├── ARCHITECTURE.md             # 系统边界、一级模块职责、跨模块拓扑
│   │   ├── INTERFACES.md               # 系统对外接口与跨模块关键通信契约
│   │   ├── ALGORITHM.md                # 全局通用算法框架与计算流
│   │   ├── WORKFLOW.md                 # 端到端业务闭环、双阶段状态机与容错
│   │   └── DATA_DICTIONARY.md          # 公共数据语义登记 (Recipe、State、Tokens)
│   ├── verification/
│   │   └── TESTING.md                  # 系统测试策略、端到端与跨模块验证策略
│   ├── decisions/
│   │   └── DECISIONS.md                # 系统级架构决策记录 (ADR 汇总)
│   └── standards/                      # 强制性规范与可选通用规则
│       ├── DOCUMENT_RULES.md           # 本文件：文档组织与编写规范
│       ├── COMMENT_RULES.md            # 代码注释规范与防冗余要求
│       ├── TRACEABILITY_RULES.md       # 需求-设计-代码-测试编号与追踪规范
│       ├── CHANGE_VALIDATION.md        # 变更一致性校验流程与合入条件
│       ├── API_RULES.md                # 统一接口命名、错误码与契约风格
│       ├── DATA_RULES.md               # 统一时间、单位、标识符与空值规则
│       ├── UI_RULES.md                 # 统一 Atelier 视觉风格与 Design Tokens 原则
│       └── TEST_RULES.md               # 统一测试命名、隔离与断言规范
│
└── src/                                # 【模块级文档】内部实现闭环
    ├── core/
    │   ├── docs/                       # 一级模块抽象层与核心管线文档
    │   ├── plate/docs/                 # 领域核心物理仿真算法与单测文档
    │   └── hatching/docs/              # 领域核心神经流线微分几何算法文档
    ├── orchestration/docs/             # 调度、缓存、DAG 与导出模块文档
    ├── services/docs/                  # 本地/客户端网关与服务降级文档
    └── ui/docs/                        # 前端界面、两阶段工坊与交互规范 (UI_DESIGN.md)
```

## 2. 根 `docs/` 与模块 `docs/` 的职责边界

| 文档类型 | 根 `docs/` 中的职责 | 模块 `docs/` 中的职责 | 设计边界与权威原则 |
| :--- | :--- | :--- | :--- |
| **`README.md`** | 提供系统文档、规范、模板及一级模块文档导航。 | 提供本模块文档、上级依据及二级模块导航。 | 负责**文档索引**，不承担项目运行安装说明。 |
| **`REQUIREMENTS.md`** | 定义系统目标、完整业务场景、全局质量要求和系统验收标准。 | 细化模块能力、边界和模块验收标准。 | 模块需求必须关联上级编号（`REQ-xxx`），不擅自改变系统要求。需求文档只在根 `docs/` 中建立全局总册。 |
| **`ARCHITECTURE.md`** | 定义系统边界、一级模块职责、依赖方向和跨模块协作。 | 定义内部结构、子模块职责、内部依赖和实现约束。 | 根文档不展开模块内部私有实现细节。 |
| **`INTERFACES.md`** | 描述系统对外接口及跨模块契约的归属和协作关系。 | 定义本模块提供的契约、使用的外部契约及内部关键接口。 | **同一契约只保留一个权威定义**，其他使用方只引用，不复制。 |
| **`ALGORITHM.md`** | 描述全系统共同遵守的算法框架，或跨模块计算方案。 | 描述本模块关键算法、数学推导、正确性条件、复杂度和边界。 | 局部专有算法留在模块；根文档不能变成算法流水账汇编。 |
| **`WORKFLOW.md`** | 描述端到端业务流程、跨模块状态协作及失败恢复。 | 描述模块内部流程、状态机、并发和异常处理。 | 上下级通过明确的输入、输出和状态枚举严格衔接。 |
| **`DATA_DICTIONARY.md`** | 定义系统拥有的公共数据语义，登记共享数据的归属。 | 定义模块拥有的实体、字段、约束及数据映射。 | 使用其他模块的数据时显式引用，不复制重复定义。 |
| **`TESTING.md`** | 制定系统测试策略，设计端到端及跨模块验证，关联系统验收。 | 设计单元、模块集成和契约测试，关联模块验收。 | 根文档关注整体是否成立，模块文档关注局部实现是否正确。 |
| **`UI_DESIGN.md`** | (仅由 `standards/UI_RULES.md` 规定全局视觉标准)。 | 定义具体页面、组件、操作流、实时展示及异常反馈。 | 全局交互规则统一引用；无 UI 的模块不设立此文档。 |
| **`DECISIONS.md`** | 记录系统级技术选择、模块边界及公共约定的重大决策。 | 记录内部结构、算法和实现方案的局部决策。 | 凡影响其他模块的技术决策，必须上升到系统级 DECISIONS.md。 |

## 3. 单一真理源 (SSOT) 与引用格式规范

1. **唯一性规则**：
   任何数据结构、接口参数列表、错误码或数学方程，全库**只允许在一处文档**被完整详尽地权威定义。
2. **跨文档引用语法**：
   在其他模块使用该契约时，采用相对路径链接引用，不得复制粘贴：
   ```markdown
   > **依赖契约**：参见 [docs/design/INTERFACES.md#IF-PIPE-001](../../docs/design/INTERFACES.md#IF-PIPE-001)
   ```
3. **权威归属划分**：
   * 物理腐蚀偏微分方程：权威在 `src/core/plate/docs/ALGORITHM.md`
   * 调色板与 Design Tokens：权威在 `docs/standards/UI_RULES.md`
   * 刻版数据结构 `RecipeSchema`：权威在 `docs/design/DATA_DICTIONARY.md`
   * 调度器时序与 DAG 剪枝：权威在 `src/orchestration/docs/ARCHITECTURE.md`

## 4. 章节结构与 Markdown 格式规范

所有文档必须包含标准头部元数据，章节层级使用 ATX 标题（`#`, `##`, `###`）：

```markdown
# 文档标题 (DOC_IDENTIFIER)

> **模块归属**：[模块路径]  
> **上级依据**：[指向根设计或上级文档的相对链接]  
> **最新状态**：正式发布 / 维护中  
> **权威追踪**：REQ-xxx / DES-xxx  

---

## 1. 概述与核心职责
...
```

* **禁止事项**：
  * 禁止在正文中使用未转义的 HTML 标签（除必要的高级格式外）；
  * 禁止直接硬编码绝对路径（如 `D:\workshop\...`），统一使用相对于仓库根目录的相对路径或代码仓路径；
  * 禁止包含任何未经解释的“TODO / TBD”无主孤儿文本。
