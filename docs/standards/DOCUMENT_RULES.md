# Etchloom 文档系统规范

## 1. 目的与范围

本规范定义 Etchloom 文档系统的组织方式：目录结构、文档类型与职责、章节骨架、状态管理、权威来源、追溯关联和变更纪律。

- **目标**：同一事实在全库只有一个权威定义；任何文档的归属、状态和适用性可由门禁机械化判定；代码、注释、文档三者保持一致。
- **适用对象**：根项目与全部一级模块（当前为 `core`、`orchestration`、`services`、`ui`）。二级子模块不建立 `docs/` 目录（§3.3）。

## 2. 设计原则

1. **唯一权威**：同一事实只有一个 Active 状态的权威定义，其余位置引用。归属判定与冲突仲裁见 §7。
2. **层级分工**：根级定义系统级事实与规范，模块级定义模块内部事实。根级不展开模块内部细节，模块级不重定义系统级事实。
3. **骨架先行**：每种文档类型有固定章节骨架（§5）。状态头、文档 ID、权威关系节缺失为门禁 error；正文章节的顺序与缺失为 warning。
4. **追溯闭环**：需求、设计、代码、测试通过 ID 关联，关联格式以 `standards/TRACEABILITY_RULES.md` 为准。
5. **简洁对外**：模块对外接口可以是函数式接口或面向对象接口，具体取决于场景。函数式接口适合无状态的工具函数（如算法模块），面向对象接口适合状态管理和响应式流（如工作流、UI 层）。复杂性对内隐藏，接口纪律见 §5.4。
6. **发现即修**：发现代码与需求、设计、文档不一致时，必须在同一次变更中同步调整。不存在宽限期，不存在"先提交后补文档"。

## 3. 目录结构

### 3.1 根 docs/

```text
docs/
├── README.md                     系统文档导航与权威索引
├── requirements/
│   └── REQUIREMENTS.md           系统需求（唯一权威，含分模块章节）
├── design/
│   ├── ARCHITECTURE.md           系统边界、模块职责、依赖方向
│   ├── INTERFACES.md             跨模块契约归属登记（登记与定义分离，§7.3）
│   ├── ALGORITHM.md              全系统共同遵守的算法约束（条件必填，§4.2）
│   ├── WORKFLOW.md               端到端业务流程与跨模块状态协作
│   └── DATA_DICTIONARY.md        公共数据语义与共享数据归属登记
├── verification/
│   ├── TESTING.md                系统测试策略与端到端验证
│   ├── reports/                  系统级验证报告（Report 状态）
│   └── evidence/                 系统级验证证据（截图、录屏等）
├── decisions/
│   └── DECISIONS.md              系统级重大决策与冲突仲裁记录
└── standards/
    ├── DOCUMENT_RULES.md         本文件
    ├── CODING_RULES.md           编码与格式规范
    ├── COMMENT_RULES.md          代码注释规范
    ├── TRACEABILITY_RULES.md     追溯 ID 规范
    ├── CHANGE_VALIDATION.md      变更校验规范
    └── （条件规范：API_RULES / DATA_RULES / UI_RULES / TEST_RULES，§4.2）
```

### 3.2 一级模块 docs/

```text
<module>/docs/
├── README.md                     模块文档导航、上级依据、豁免声明（§4.3）
├── design/
│   ├── ARCHITECTURE.md           内部结构、子模块职责、实现约束
│   ├── INTERFACES.md             对外函数式接口（条件必填，§4.2、§5.4）
│   ├── ALGORITHM.md              本模块关键算法（条件必填）
│   ├── WORKFLOW.md               内部流程、状态机、并发与异常（条件必填）
│   ├── DATA_DICTIONARY.md        本模块拥有的实体与字段（条件必填）
│   └── UI_DESIGN.md              页面与交互方案（仅 UI 模块）
├── verification/
│   ├── TESTING.md                单元、集成与契约测试设计
│   ├── reports/                  模块级验证报告（Report 状态）
│   └── evidence/                 模块级验证证据
└── decisions/
    └── DECISIONS.md              模块内部局部决策
```

模块 docs 不含 `requirements/` 与 `standards/`：需求唯一权威在根级 `REQUIREMENTS.md` 的分模块章节（§5.2），规范只在根级。

### 3.3 禁止项

门禁对以下结构报 error，不得绕过：
1. 模块 `docs/` 下不得出现 `requirements/`、`standards/` 目录。
2. 二级子模块不得建立 `docs/` 目录；子模块 README 是唯一允许的文档载体。
3. 不得在 §4 矩阵之外新增文档类型。文档类型的增删是元规范变更，走 §10 流程。
4. 条件必填文档（§4.2）触发时必须与代码同次变更建立；未触发时不得建立占位文档。空文档是最坏的状态——读者无法区分"缺失"和"无内容"。豁免在模块 README 中显式声明（§4.3），不用空文件表达。
5. `docs/` 内不得存放截图、录屏等二进制证据。证据归 `verification/evidence/`，文档以相对路径引用，不内嵌。

### 3.4 元数据规范

所有文档必须以 YAML front matter 开始，定义机器可读的元数据。front matter 位于文件最前部，以 `---` 包围，采用标准 YAML 语法。

#### 3.4.1 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `title` | string | 是 | 文档标题，与 H1 一致 |
| `status` | enum | 是 | Active / Draft / Superseded / Report |
| `doc-id` | string | 是 | 追溯 ID，格式：`<类型>-<模块>` 或 `RULE-<类型>`，如 `RULE-DOC`、`DATA-SYS`、`ARCH-SYS` |
| `owner-module` | string | 是 | 属主模块标识：`root` 或模块名（core / orchestration / services / ui） |
| `superseded-by` | string | 条件 | 仅当 `status: Superseded` 时必填，值为替代文档的相对路径 |
| `verification-command` | string | 条件 | 仅当文档包含可执行验收标准时必填，值为 PowerShell 命令字符串 |
| `created` | ISO 8601 | 是 | 文档建立时的时间快照；旧文档可由迁移工具用 Git 首次提交时间初始化 |
| `modified` | ISO 8601 | 是 | 最近一次编辑文档时的时间快照；实际最后提交时间以 Git 历史为准 |

#### 3.4.2 时间戳派生规则
- 新文档建立时填写 `created`，每次编辑文档时更新 `modified`；两者是文档内容的一部分，不要求等于提交时间。
- 迁移旧文档时，工具可以用 Git 的首次提交和最后提交时间初始化这两个字段；此后不反复同步。
- 查询实际入库时间和最后提交时间，应直接使用 `git log`。提交时间直到提交完成才确定，要求文档中的 `modified` 精确等于自身最后提交时间无法稳定满足。
- 校验脚本保持只读，检查字段存在、ISO 8601 格式和 `created <= modified`，不批量改写文档。

#### 3.4.3 校验级别
- **Error**（阻塞合并）：缺失必填字段、`status` 值非法、`superseded-by` 指向不存在的文件、`doc-id` 重复；
- **Warning**（提示不阻塞）：`modified` 早于 `created`（时间悖论）、条件必填字段在状态满足时缺失、字段顺序不符合 §3.4.1 表序。

#### 3.4.4 与引用块格式的关系
现有 `> 状态：Active` 引用块为**遗留格式**，新文档必须使用 YAML front matter。迁移策略：门禁识别 YAML front matter 为唯一合法格式，引用块格式报 Warning 并提示迁移，不阻塞现有文档。

#### 3.4.5 示例

```yaml
---
title: Etchloom 文档系统规范
status: Active
doc-id: RULE-DOC
owner-module: root
created: 2026-10-08T19:31:17+08:00
modified: 2026-10-10T20:25:00+08:00
---
```

## 4. 文档类型总表

### 4.1 固定文档

以下文档在适用层级必须存在，无条件豁免：

| 文档 | 根 | 一级模块 | 职责边界 |
|---|---|---|---|
| README.md | ✓ | ✓ | 文档导航与权威索引；不承担项目使用说明 |
| requirements/REQUIREMENTS.md | ✓ | — | 系统目标、业务场景、全局质量要求、系统验收、分模块需求 |
| design/ARCHITECTURE.md | ✓ | ✓ | 根：模块职责与依赖方向；模块：内部结构与实现约束 |
| design/WORKFLOW.md | ✓ | — | 根：端到端流程与跨模块状态协作 |
| design/DATA_DICTIONARY.md | ✓ | — | 根：公共数据语义与共享数据归属登记 |
| design/UI_DESIGN.md | — | 仅 UI 模块 | 具体页面、组件、操作、展示及异常状态 |
| verification/TESTING.md | ✓ | ✓ | 根：系统测试策略；模块：单元/集成/契约测试设计 |
| decisions/DECISIONS.md | ✓ | ✓ | 根：系统级决策与仲裁；模块：局部决策 |
| standards/*.md | ✓ | — | 规范只在根级 |

### 4.2 条件必填文档

| 文档 | 触发条件（门禁可判定） |
|---|---|
| 模块 design/INTERFACES.md | 模块公开符号出现在另一模块源码中（门禁静态分析 import 关系判定） |
| 模块 design/ALGORITHM.md | 模块含非平凡算法（判定标准：存在黄金样本测试或正确性条件无法用一句话陈述） |
| 模块 design/WORKFLOW.md | 模块含内部状态机、并发调度或异步恢复逻辑 |
| 模块 design/DATA_DICTIONARY.md | 模块拥有被其他模块消费的数据实体 |
| 根 design/ALGORITHM.md | 存在 ≥2 个模块必须共同遵守的算法约束 |
| standards/UI_RULES.md | 存在 ≥1 个 UI 模块，或存在跨模块交互规则 |
| standards/API_RULES.md | ≥2 个模块需要统一接口风格 |
| standards/DATA_RULES.md | ≥2 个模块共享横切数据表达约定（具体 schema 归 design/DATA_DICTIONARY 类文档；当前无独立横切规则时文档保持 Superseded） |
| standards/TEST_RULES.md | ≥2 个模块需要统一测试方法 |

### 4.3 条件豁免声明

条件必填文档未建立时，模块 README 必须在对应导航位置声明豁免，格式：

```markdown
- INTERFACES.md：未触发（本模块公开符号当前未被其他模块 import）
```

门禁检查：触发条件成立而文档缺失且无豁免声明 → error；豁免声明与事实不符（声明未触发但 import 关系存在）→ error。

## 5. 章节骨架

所有文档以 YAML front matter 开始（§3.4），后接 H1 标题与正文。章节骨架如下：

### 5.1 README.md

根与模块共用骨架：

```markdown
## 文档导航（本层级文档清单：类型 + 链接 + 状态 + 一句话用途；条件必填文档含豁免声明）
## 上级依据（模块必填：本模块承接的需求章节锚点、适用的规范清单；根级此节省略）
## 权威关系（本层级哪些事实是权威，哪些事实引用其他层级；README 本身不承载权威定义）
```

README 只提供索引与导航，不承担项目使用说明，不重复任何文档的正文内容。

### 5.2 requirements/REQUIREMENTS.md（仅根级）

```markdown
## 1. 系统目标（一段：系统解决什么问题，面向谁，不做什么）
## 2. 业务场景（编号场景：场景 ID + 角色 + 触发 + 期望结果。场景是验收的叙事单位，不是功能列表）
## 3. 全局质量要求（性能、可用性、可观测性等横切要求，每条带可度量指标）
## 4. 系统验收标准（编号 AC-SYS-xxx：端到端可判定的通过条件，关联 §2 场景）
## 5. 分模块需求（每模块一节）
### 5.x <模块名>
#### 5.x.1 承接的系统需求（引用 §2 场景 ID 与 §4 AC ID 列表——只列 ID，不复述）
#### 5.x.2 模块能力需求（REQ-<模块>-xxx：能力描述 + 边界（不做什么）+ 来源。 来源必填：细化自某场景 / 模块特有。模块特有需说明理由）
#### 5.x.3 模块验收标准（AC-<模块>-xxx：可判定通过条件，关联 5.x.2 需求 ID）
```

模块文档引用需求时链接到本节锚点；模块内不得复述需求正文。

### 5.3 design/ARCHITECTURE.md

根级：

```markdown
## 1. 系统边界（系统与外部世界的接缝）
## 2. 系统架构图（命令行终端风格的 ASCII 架构图，展示模块依赖关系和数据流）
## 3. 模块职责（每模块一行：职责 + 不做什么）
## 4. 文件结构树（模块的文件结构树，标注关键文件和目录）
## 5. 依赖方向（依赖图 + 禁止的反向依赖）
## 6. 跨模块协作（关键协作关系概述，细节链到 WORKFLOW / INTERFACES）
## 7. 权威契约索引（跨模块事实的权威位置清单）
```

模块级：

```markdown
## 1. 模块定位（承接的需求 ID 列表 + 在系统中的角色）
## 2. 模块架构图（命令行终端风格的 ASCII 架构图，展示内部组件和数据流）
## 3. 内部结构（子模块/分层划分与各自职责）
## 4. 文件结构树（模块的文件结构树，标注关键文件和目录）
## 5. 内部依赖（子模块间依赖方向与禁止项）
## 6. 实现约束（平台限制、性能预算、线程模型等对实现有约束力的决策）
## 7. 对外边界（公开入口列表，链到 INTERFACES.md；不重复接口定义）
```

**架构图要求**：
- 使用命令行终端风格的 ASCII 字符（如 `├──`、`└──`、`│`、`▼`、`►`）
- 展示组件之间的依赖方向和数据流
- 标注关键组件的职责
- 保持简洁，不超过 20 行

**文件结构树要求**：
- 使用 `tree` 命令风格的缩进和符号
- 标注关键文件（如入口文件、配置文件、核心实现）
- 省略不重要的文件（如测试文件、构建产物）
- 保持简洁，不超过 30 行

根级 ARCHITECTURE.md 不得展开模块内部细节；模块级不得重定义模块职责与依赖方向。

### 5.4 design/INTERFACES.md

对外接口的唯一权威文档。核心纪律：
- **粒度**：每个子模块默认对外暴露恰好一个入口（函数或接口）。多于一个时，每增加一个接口必须附一段"为何无法合并"的理由。
- **形式**：接口可以是函数式接口（`fun processImage(...)`）或面向对象接口（`interface EvaluationWorkflow { ... }`），具体取决于场景：
  - **函数式接口**：适合无状态的工具函数（如算法模块），签名简洁，易于测试
  - **面向对象接口**：适合状态管理和响应式流（如工作流、UI 层），通过 StateFlow/Flow 或回调管理状态
- **简洁**：本文件只写签名、语义、边界。禁止出现内部类型、中间数据结构、实现私有签名；调用示例不得超过 5 行（示例过长是接口不够简洁的信号）。
- **单向**：只写"本模块提供什么"。消费关系由调用方在自己的文档中引用，本文件不设"使用的外部契约"章节。

骨架（函数式接口）：

```markdown
## 1. 接口清单
| 子模块 | 入口函数 | 权威定义（源码符号） | 输入 | 输出 |
（一行一个，签名级简洁）

## 2. 接口契约
### 2.x <子模块>.<函数名>
- 签名：（完整函数签名，代码块）
- 语义：（输入含义、输出含义，一段以内）
- 正确性条件：（前置条件、后置条件、不变式）
- 失败行为：（错误如何表达，调用方如何感知）
- 取消与并发：（如适用：取消语义、作用域）
- 变更历史：（破坏性变更记录，链到 decisions）
### 2.y 附加接口的理由（仅当子模块存在第二个及以上接口时：为何无法合并为一个函数）
```

骨架（面向对象接口）：

```markdown
## 1. 接口清单
| 接口类型 | 接口名称 | 权威定义（源码符号） | 说明 |
（一行一个，签名级简洁）

## 2. 接口契约
### 2.x <接口名称>
- 签名：（完整接口定义，代码块）
- 语义：（接口职责、成员说明）
- 正确性条件：（前置条件、后置条件、不变式）
- 失败行为：（错误如何表达，调用方如何感知）
- 取消与并发：（如适用：取消语义、作用域）
- 变更历史：（破坏性变更记录，链到 decisions）
### 2.y 附加接口的理由（仅当存在第二个及以上接口时：为何无法合并为一个接口）
```

### 5.5 design/ALGORITHM.md

```markdown
## 1. 算法清单（名称 + 用途 + 权威实现位置）
## 2. 算法定义（每个算法一节：问题陈述、输入输出、正确性条件、复杂度、边界与失败行为）
## 3. 验证策略（黄金样本、性质测试等正确性保障手段，链到 TESTING.md）
```

根级只收录全系统共同遵守的算法约束，不变成算法汇编；局部算法留在模块文档。

### 5.6 design/WORKFLOW.md

```markdown
## 1. 流程总览（端到端步骤图）
## 2. 状态模型（状态定义、转移条件、终态）
## 3. 跨模块协作 / 内部协作（各步骤的属主模块、输入、输出；上下级通过明确的输入输出和状态衔接）
## 4. 失败与恢复（失败注入点、重试策略、中断恢复语义）
```

### 5.7 design/DATA_DICTIONARY.md

```markdown
## 1. 数据归属总表（实体 + 属主模块 + 权威定义位置。使用他方数据时引用，不复制定义）
## 2. 实体定义（每个实体一节：字段、类型、单位、约束、空值语义、序列化格式）
## 3. 数据映射（跨边界映射关系：持久化 ↔ 内存 ↔ 传输，各方权威位置）
```

### 5.8 design/UI_DESIGN.md（仅 UI 模块）

```markdown
## 1. 信息架构（页面清单与导航关系，全局规则引用 standards/UI_RULES.md）
## 2. 页面规范（每页一节：结构、内容、操作、展示规则）
## 3. 组件规范（跨页面复用组件的行为与外观）
## 4. 状态与异常（加载、空态、错误、权限等状态的呈现）
```

### 5.9 verification/TESTING.md

模块级 `docs/verification/TESTING.md` 是该模块测试现状的权威清单，其章节骨架、测试矩阵列要求、对抗性测试体现、禁止项由 `TEST_RULES` 唯一定义。

根级 `docs/verification/TESTING.md` 是系统测试策略（测试分层、强制规则集、回归命令、模块分工），按主题组织，至少包含：

```markdown
## 1. 测试策略（分层与目标：根级关注整体是否成立；覆盖性/对抗性测试分层）
## 2. 测试范围（系统级用例清单，每条关联需求/验收 ID，格式以 TRACEABILITY_RULES.md 为准）
## 3. 替身与环境（fake 设计、设备依赖、环境前提）
## 4. 验证报告（reports/ 索引：日期 + 链接 + 结论）
## 5. 验证证据（evidence/ 索引与引用规则；证据只用于复核报告结论，不作为设计或交互契约）
```

模块级与根级 TESTING.md 的分工：根级定「要测什么、为什么」，模块级定「本模块测了什么、怎么写」。

### 5.11 standards/ 规范文档

规范文档（`standards/*.md`，doc-id 均为 `RULE-<类型>`）按职责分为四类，每类有专属章节骨架。新增规范必须先归类、再套用对应骨架；本节是各类骨架的唯一权威定义。

四类与现有规范的对应：

| 规范形态 | 规范名称 | doc-id |
|---|---|---|
| 元规范 | DOCUMENT_RULES.md | RULE-DOC |
| 规则集型 | CODING_RULES.md / COMMENT_RULES.md / TEST_RULES.md / API_RULES.md / UI_RULES.md | RULE-CODING / RULE-COMMENT / RULE-TEST / RULE-API / RULE-UI |
| 追溯型 | TRACEABILITY_RULES.md | RULE-TRACE |
| 流程型 | CHANGE_VALIDATION.md | RULE-CHANGE |
| （存根/横切） | DATA_RULES.md | RULE-DATA |

**所有规范文档的共同硬性要求**（门禁可判定）：
1. YAML front matter：`title` / `status` / `doc-id: RULE-<类型>` / `owner-module` / `created` / `modified`；
2. 第一章为「目的」或「目的与范围」：说清管什么、不管什么（划界）；
3. 规则可判定：每条规则指向可机械检查的工件（命令、正则、清单、表格），禁止不可判定的口号；
4. 末章或次末章为「与其他规范的关系」：划界引用而非复述，冲突时以本文件 §9 为准；
5. 引用其他规范用链接锚点（如 `TRACEABILITY_RULES §2.5`），不复制其内容。

#### 5.11.1 元规范（DOCUMENT_RULES.md 自身）
元规范定义文档系统的组织方式，是其他一切文档形态的来源。骨架见本文件目录与章节结构。

#### 5.11.2 规则集型规范（CODING / COMMENT / TEST / API / UI）
针对某一横向领域给出一组可判定规则。三段式骨架：

```markdown
## 1. 目的与范围        （本规范管哪个领域；明确把相邻领域排除给谁；适用模块）
## 2. 规则正文          （按主题分二级小节 §2.1/§2.2…；每条规则带类型字母编号）
## 3. 与其他规范的关系   （划界引用；冲突仲裁）
```

**编号约定**：规则用「类型字母 + 数字」连续编号（CODING 用 `C`、COMMENT 用 `K`），便于反引（如 `C5`、`K2`）。TEST_RULES 强制规则集由根 `verification/TESTING.md` 权威定义。

#### 5.11.3 追溯型规范（TRACEABILITY_RULES）
定义全库追溯 ID 的格式与关联格式。骨架：

```markdown
## 1. 目的              （建立需求-设计-代码-测试的 ID 关联；变更影响可定位）
## 2. ID 命名规则        （逐类定义 REQ/AC/SCEN/T/D/文档 ID 六类：格式 + 示例 + 唯一性规则）
## 3. 关联格式          （五种关联方向的书写格式：需求→场景/验收→场景/测试→需求/决策→需求/代码→设计）
## 4. 引用 vs 定义       （权威定义唯一，引用链接不复述，杜绝双权威）
## 5. 代码符号定位       （类/函数/文件三层定位语法）
## 6. 跨模块引用        （只能引用公开契约；依赖方向符合架构）
## 7. 文件移动和删除     （同次变更更新全部引用；checkbox 检查清单）
## 8. 门禁检查          （ID 存在性/引用完整性/重复定义三类机械检查及判定方式）
## 9. 工具支持          （全文搜索与门禁脚本命令）
## 10. 最佳实践         （ID 命名/引用/变更的软建议，非门禁判定）
## 11. 与其他规范的关系  （本规范是六类 ID 格式的唯一权威；规则含义/必填性/变更同步分别让渡）
```

#### 5.11.4 流程型规范（CHANGE_VALIDATION）
定义「变更时如何保证代码/注释/文档一致」的流程。表格与清单驱动，骨架：

```markdown
## 1. 目的              （保证代码/注释/文档一致；禁止先变更后补文档；机械化验证）
## 2. 变更影响判断      （变更类型表：类型→影响范围→必更文档；流程图固化判定步骤）
## 3. 变更触发的文档更新 （代码变更触发 / 文档变更触发两张映射表）
## 4. 检查命令          （变更前/中/后三阶段命令与 checkbox 清单）
## 5. 合并条件          （准入 checklist 与禁止合并情形 ❌ 清单）
## 6. 评审职责          （变更者 / 评审者双视角职责清单）
## 7. 例外处理          （紧急/实验/遗留三类例外：定义 → 流程 → 禁止行为；紧急无宽限期）
## 8. 工具支持          （门禁脚本含 -WarnOnly / 测试命令 / 文档搜索）
## 9. 最佳实践          （变更前/中/后与持续改进软建议）
## 10. 与其他规范的关系 （自定位为本文件 §2「发现即修」的执行细则）
```

#### 5.11.5 已迁移/存根规范（Superseded）
当一份规范的内容被判定不属于 `standards/`（如纯数据格式 schema），按本文件 §10 迁移后，原文档转为存根：
- `status: Superseded`，front matter 加 `superseded-by: <新权威路径>`；
- 正文只保留迁移说明（原内容去向、迁移日期、未来重建条件），**不再保留规则正文与章节骨架**。

## 6. 状态管理

状态枚举：`Active / Draft / Superseded / Report`，只有这四个词，禁止自造状态词。归档动作表达为状态变更 + 索引降级，不另设 Archived 状态。

| 状态 | 含义 | 使用规则 |
|---|---|---|
| Active | 当前权威 | 同一事实全库只能有一个 Active 权威定义 |
| Draft | 未定稿 | 可被引用但引用方自担风险；Draft 不能作为权威来源 |
| Superseded | 被取代 | 文档头必须注明替代者链接；保留供历史查阅，索引中降级到"历史"小节 |
| Report | 历史记录 | 时间快照（验证报告、审计记录），只描述当时事实，不随系统演进更新 |

转换规则：
- Draft → Active：评审通过后，同次变更更新所有引用方的链接指向。
- Active → Superseded：替代文档必须同次变更就绪，禁止出现权威真空期。
- 任何状态 → Report：仅适用于快照类文档（验证报告、审计记录）；规范与设计文档不得转为 Report。

## 7. 权威来源与冲突仲裁

### 7.1 唯一权威原则
同一事实全库只有一个 Active 状态的权威定义。其他文档需要该事实时，以"链接 + 章节号"引用，禁止整段复制。例外：契约的函数签名允许在模块 README 中重复出现一次（导航目的），但必须标注"详见"链接。

### 7.2 归属判定优先级
事实归属不明确时，按以下优先级判定：
1. 数据属主：谁持久化，谁定义格式（DATA_DICTIONARY 归属）；
2. 实现属主：谁实现算法或流程，谁定义行为（ALGORITHM / WORKFLOW 归属）；
3. 调用方不拥有权威：调用方文档只能引用，不得重新定义。

### 7.3 跨模块事实的升级规则
事实影响范围超出单个模块时（≥2 个模块依赖），权威定义上升到根级：
- 跨模块契约 → 根 INTERFACES.md 登记归属，定义仍在实现方（登记与定义分离：根级只登记"哪个模块拥有哪个契约"，不复制契约内容）；
- 跨模块算法约束 → 根 ALGORITHM.md；
- 跨模块交互规则 → standards/UI_RULES.md。

### 7.4 冲突仲裁流程
1. 发现两处文档对同一事实定义不一致时，不得直接修改任一方覆盖另一方；
2. 在根 decisions/DECISIONS.md 创建条目，记录：冲突双方位置、各自立场、影响范围、建议权威方；
3. 评审确认前，双方文档相关章节标记 Draft；
4. 仲裁结论生效后，败方删除定义改为引用，并在同一次变更中完成。

## 8. 追溯关联

需求、设计、代码、测试之间的关联 ID 命名、定义与引用的区别、关联格式、代码符号定位、跨模块引用、文件移动删除后的处理，以 `standards/TRACEABILITY_RULES.md` 为唯一权威。本文件不重复定义，仅规定两条底线：
1. 模块能力需求必须携带来源标记（细化自某场景 / 模块特有，§5.2），使根级需求的模块映射可机械化校验；
2. 测试用例必须关联需求或验收 ID，无关联 ID 的用例视为策略外测试，不计入覆盖。

## 9. 与其他规范的关系

- 文本编码、行尾、缩进、命名、导入顺序，以 `standards/CODING_RULES.md` 为准；
- 代码注释的职责、写法、何时解释设计原因、如何引用文档，以 `standards/COMMENT_RULES.md` 为准；
- 追溯 ID 与关联格式以 `standards/TRACEABILITY_RULES.md` 为准；
- 变更影响判断、变更触发的文档更新、检查命令与合并条件以 `standards/CHANGE_VALIDATION.md` 为准；
- 各规范内容冲突时，以本文件为准并立即修正冲突方。

## 10. 变更流程

本文件的修改是元规范变更，要求：
1. 在根 decisions/DECISIONS.md 立项，记录变更动机与影响面；
2. 评审通过后，同一次变更内完成：本文件更新 + 受影响文档的同步调整 + 门禁规则更新；
3. 禁止"先改结构后补规范"：文档类型、目录层级、状态枚举、元数据字段的新增必须先改本文件。

## 11. 门禁脚本职责

`docs/check-documentation.ps1` 承担以下元数据相关职责：
- **校验**：检查 YAML front matter、必填字段、枚举值、引用有效性、时间戳格式与先后顺序；
- **报告**：按 Error / Warning 分级输出，Error 阻塞合并，Warning 提示迁移。门禁脚本只读，不修改正文或 front matter；批量迁移由独立迁移脚本负责。实际提交时间从 Git 历史查询，不复制回文档元数据。
