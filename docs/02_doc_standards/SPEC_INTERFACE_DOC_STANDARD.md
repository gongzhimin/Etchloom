# 模块接口设计与契约规范书写工程规范 (SPEC_INTERFACE_DOC_STANDARD.md)

> **位置**：`docs/02_doc_standards/SPEC_INTERFACE_DOC_STANDARD.md`  
> **适用范围**：存放在各模块下的 `docs/INTERFACE_SPEC.md` 以及全局通信协议规范。  
> **核心原则**：**契约先行（Design by Contract）、指导实现而非事后描述代码、定义应然而非复述现状**。

---

## 1. 核心指导思想：规范性契约 vs 事后代码描述

在严肃的软件工程与体系化架构设计中，接口文档必须作为**指导代码实现的根本蓝图**，严禁沦为“事后代码描述的流水账”。编写者必须深刻理解并严格执行以下原则：

| 维度 | ❌ 事后代码描述（严厉禁止的反模式） | ✅ 契约规范设计（唯一合规的工程标准） |
| :--- | :--- | :--- |
| **视角定位** | **事后旁观者视角**：“代码怎么写我就怎么抄”。 | **系统设计者视角**：“根据系统目标，模块必须提供什么契约承诺”。 |
| **内容取向** | 纠缠于局部语法糖与实现细节（如 for 循环、临时局部变量、内部私有辅助逻辑）。 | 专注于公开能力抽象、强类型签名、前置约束与后置状态保障。 |
| **生命力** | **极度脆弱**：代码稍微重构或算法由 JS 替换为 WebAssembly，文档立即失效腐烂。 | **持久稳固**：只要数学契约与对外接口不变，实现细节任意重构升级，文档依然是金标准。 |
| **工程效用** | 开发者无法从中推导出边界容错与不变量，只能当作低效的代码阅读注释。 | 开发者依据文档即可独立编写代码、设计单测、进行静态类型检查与 Mock 仿真。 |

---

## 2. 接口设计文档必须包含的 7 大标准章节

所有存放在子模块 `docs/INTERFACE_SPEC.md` 中的接口设计文档，必须严格包含以下 7 大规范章节：

```markdown
# [模块/子系统名称] 接口设计与契约规范 (INTERFACE_SPEC.md)

## 1. 接口设计哲学与职责边界 (Design Philosophy & Boundary)
- 说明本模块对系统暴露的最小必要能力集；
- 明确哪些内部状态严格私有封装，哪些能力对外开放；
- 明确禁止的反向依赖与越权操作（如物理引擎严禁接触 DOM，管线算子严禁持有网络连接）。

## 2. 强类型接口定义与数据结构契约 (Type Definitions & Data Contract)
- 使用精确的 TypeScript / IDL 接口声明所有参数与返回值；
- 明确只读不可变约束（Readonly<T>）、空值语义（Nullability）与量纲单位（如归一化标量 [0.0, 1.0]、连续一维平铺 TypedArray 内存网格）。

## 3. 前置条件与参数合法性约束 (Pre-conditions)
- 调用方在发起方法调用前必须满足的前置状态约束（如：宽度高度必须为正整数、输入像素缓冲区长度必须严格等于 W * H * 4）；
- 防御性校验标准：面对违反前置条件的非法调用，接口应如何断言或抛出类型化错误（TypeError / RangeError）。

## 4. 后置条件与状态变更承诺 (Post-conditions)
- 实现方在成功返回时必须向调用方做出的数学与物理状态承诺（如：所有输出矢量折线顶点坐标严格落入 [0, W) x [0, H) 包围盒内、输出 ArrayBuffer 保持字节对齐、未选定区域的刻痕深度严格守恒为 0）。

## 5. 系统不变量与守恒律 (System Invariants)
- 在任何公共方法调用前后，模块必须保持恒真的条件（如：流线拓扑互不相交性、双缓冲平铺网格的一维行优先索引一致性、全局图层顺序单调递增性）。

## 6. 纯函数属性、副作用与内存所有权 (Side-effects & Memory Ownership)
- 明确接口是否为纯函数（无任何外部可见副作用）；
- 涉及连续 TypedArray 或大对象时，明确内存所有权是转移（Transfer）、借用（Borrow）还是深拷贝（Deep Copy），避免内存泄漏与意外并发篡改。

## 7. 错误契约、并发与生命周期状态协议 (Error Handling & Lifecycle Protocol)
- 异常抛出类型、错误码或降级哨兵值规范；
- 异步接口的 AbortSignal 抢占中止协议、防抖重入保证与幂等性（Idempotence）规范。
```

## 3. 语言措辞与书写规范红线

1. **统一使用规范性指导动词**：
   - 必须使用 **MUST / SHALL / 必须**：表示接口实现方必须强制遵循的硬性契约；
   - 必须使用 **MUST NOT / SHALL NOT / 严禁**：表示接口绝对不能做出的危险行为（如修改入参不可变只读缓冲区）；
   - 必须使用 **SHOULD / 应当**：表示实现方强烈推荐的最优实现模式；
2. **剔除流水账复述**：
   - ❌ 严禁出现：“在 `foo.js` 中定义了一个循环，每次循环都把 i 增加 1，然后放进数组...”；
   - ✅ 必须改为：“实现方必须保证输出数组的元素顺序与输入的空间拓扑排序完全一致，时间复杂度不得超过 $O(N \log N)$”；
3. **消除模糊值域**：
   - ❌ 严禁出现：“输入一个合理的深度值”；
   - ✅ 必须改为：“入参 `depth` 必须为 IEEE 754 双精度浮点数，且满足 $0.0 \le \text{depth} \le 1.0$；若传入 NaN 或越界值，接口必须抛出 `RangeError`”。
